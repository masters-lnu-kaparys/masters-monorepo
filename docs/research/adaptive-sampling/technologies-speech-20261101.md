# Текст до презентації технологій для Олійника

Canva: https://www.canva.com/design/DAHXtnF-LS8/_2C_WyrwMVaHQgMRFWCfXg/edit

Відповідає поточним 13 слайдам. Для цього предмета головний акцент - слайди
3-6 та реалізація, дослідницькі слайди 7-10 можна проходити коротше.

## 1. Тема

Добрий день. Покажу технології, які використав у системі моніторингу паркомісць:
від сенсорного вузла до вебінтерфейсу. Також коротко поясню, як у цій системі
демонструється досліджений розклад вимірювань.

## 2. Що робить система

Користувач відкриває карту, вибирає парковку та бачить стан її місць. Пристрій
надсилає виміри, сервер зберігає їх і передає оновлення у відкритий інтерфейс.
Окреме питання магістерської - коли виконувати наступний вимір. Адже між
перевірками машина може приїхати або поїхати, і карта деякий час показуватиме
попередній стан.

## 3. Вебінтерфейс

Клієнтську частину я написав на React і TypeScript. React допоміг розділити
інтерфейс на компоненти: карту, список місць, історію та форми. TypeScript
дає змогу перевіряти структуру даних між API й цими компонентами ще до запуску.

Для карти використано Leaflet і дані OpenStreetMap. Користувач може вибрати
парковку й побудувати до неї маршрут. Кнопки, поля й діалоги зроблено на
Material UI, а Vite використовується для розробки та збирання застосунку.

Поточні й історичні дані показуються окремо. Якщо свіжого виміру немає,
інтерфейс прямо це позначає, а місце не додається до кількості вільних.

## 4. Сервер і оновлення

На сервері використано C# та .NET 9. Тут є дві основні частини. Фоновий
воркер читає телеметрію з Azure IoT Hub і зберігає її. Web API відповідає
на запити браузера: повертає парковки, їхні місця та історію. Через нього
також надсилаються команди пристрою.

SignalR потрібен, щоб сервер міг сам передати новий стан відкритому браузеру.
Тобто користувачеві не потрібно щоразу перезавантажувати сторінку. Якщо
з'єднання перерветься, клієнт пробує підключитися знову й додатково періодично
перевіряє дані через API.

Старі повідомлення залишаються в історії, але не повертають поточний стан
назад. Це важливо, коли дані приходять із затримкою.

## 5. База даних

Для зберігання я вибрав SQL Server, оскільки дані мають чіткі зв'язки:
парковка містить місця, а кожне місце має історію вимірювань. Реляційна база
дає змогу задати ці зв'язки, обмеження та індекси. Наприклад, запис виміру
повинен належати конкретному місцю, а однакова пара «місце й час» не має
створювати дублікати.

Ще одна причина вибору - зручна інтеграція з .NET через Entity Framework Core.
Він пов'язує сутності програми з таблицями, а міграції описують зміни схеми.
SQL Server достатньо для цього прототипу; окремого порівняння швидкодії з
іншими базами я не проводив.

Для карти читається останній стан кожного місця. Для графіка - окремі
історичні записи. Тому нове повідомлення не стирає попередню історію.

## 6. IoT-вузол

Вузол складається з ESP32, датчика відстані HC-SR04 і перетворювача логічних
рівнів. Прошивка написана на C/C++. Вона виконує кілька спроб, усереднює
коректні відстані та застосовує два пороги, щоб стан не перемикався від
невеликих коливань біля одного порога.

Через Wi-Fi результат передається у JSON-повідомленні до Azure IoT Hub.
Для цього використано MQTT із захищеним TLS-з'єднанням. На слайді показано
скорочений приклад повідомлення. У зворотний бік можна передати команду
негайного виміру, зміни порогів або перезапуску.

Це лабораторний прототип. За відсутності коректної відстані він не повідомляє
«вільно», а сервер з часом позначає останні дані як застарілі. Нова політика
вибору часу вимірювання поки працює окремо в дослідницькому коді та браузері.

## 7. Дані для дослідження

Для перевірки розкладів використано відкриті записи Мельбурна за 2019 рік.
Дані розділено на навчання, налаштування й остаточне оцінювання. Правило
бачить тільки власні виміри; повна історія потрібна симулятору для підрахунку
часу неправильного показу. Параметри зафіксовано до остаточної перевірки.

## 8. Оцінка помилки

Наприклад, вимір показав «вільно», потім приїхала машина, а наступний вимір
ще не настав. До нього карта показує неправильний стан. За навчальною
історією оцінюю, скільки таких секунд може спричинити кожна пауза.

Враховується виміряний стан, час доби й тривалість однакових власних показів.
Для місць із малою історією локальна оцінка підтримується спільними даними
інших місць. Це й позначає модель на слайді.

## 9. Вибір наступного виміру

Далі порівнюються допустимі паузи. У формулі одиниця відповідає одному
наступному виміру, m - очікуваному часу помилки, λ - його вазі. Ділення на
тривалість паузи дає порівнянні витрати на секунду. У коді два неправильні
покази мають окремі ваги. Вибирається найменша оцінка.

Готові рішення зберігаються в таблиці. Для підсумкового правила відкалібровано
три повні таблиці; кожному місцю наперед призначається одна з них. Ваги
визначено на налаштувальних даних, а не за результатом остаточного тесту.

## 10. Результат

На 867 відокремлених місцях порівняно зі щохвилинним правилом отримано на
18,13% менше вимірів, на 13,91% менший час помилкового «вільно» і на 13,30% -
«зайнято». Водночас приблизно 0,202% вільних епізодів від хвилини не мають
нового виміру всередині. На частині місць є погіршення. Це результат
відтворення історії, з якого не визначається ресурс батареї фізичного вузла.

## 11. Прототип

Тут показано готовий вебінтерфейс. Окрема сторінка дозволяє відтворити
адаптивний розклад: перейти до наступного виміру, побачити причину паузи й
зберегти журнал. Вона працює без пристрою та серверного підключення й
дозволяє показати алгоритм на захисті.

## 12. Підсумок

керування фізичним вузлом за дослідженим розкладом».
